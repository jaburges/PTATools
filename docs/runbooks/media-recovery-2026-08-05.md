# Media recovery and library cleanup — 2026-08-05

## Summary

The site was serving 315 broken media references, mostly casualties of the
2026-05-22 uploads deletion (see `salvage/2026-05-22-media-loss/`). 123 files
were restored and the reference count fell to 67, all of which are accounted
for. The library was also de-duplicated: 39 redundant attachment rows removed,
23 attachments had their thumbnails regenerated.

The important finding is the recovery source. The SharePoint **Documents**
library on the Wilder PTSA team site contains a `WordPress Media/` folder that
mirrors the uploads tree by year and month (`WordPress Media/2018/11/CLAYFIFTHlesson.pdf`).
It held 88 of the missing files at their exact original paths. **Check this
first in any future media loss** — the salvage notes from May concluded the
2018 material was unrecoverable, and it was not.

Crawling all 141 pages, posts and products and probing every referenced media

| Group | Count | Fix |

### Access notes

- macOS privacy blocks a shell from `~/Downloads`, `~/Desktop` and
  `~/Documents` with `Operation not permitted`, which reads like an empty
  folder if you only run `find | wc -l`. Cursor needs Full Disk Access, or the
  files need copying somewhere reachable.
- The SharePoint library is **not** synced locally; only `OneDrive-Personal`
  is mounted under `~/Library/CloudStorage/`.
- `az account get-access-token --resource https://graph.microsoft.com` does not
  work for this: the CLI's delegated token returns `accessDenied` on `/sites`
  and the account has no OneDrive for Business provisioned.
- What does work is the plugin's own app-only token via
  `Azure_OneDrive_Media_Auth::get_app_access_token()` (client credentials),
  run inside a Container Apps job so the client secret never leaves the tenant.
  `/sites?search=` is still denied, but `/sites/root` and

## Running WordPress inside a job

Several steps needed WordPress bootstrapped with the plugin available. Two
things to know about the site image:

- Core lives at `/usr/src/wordpress` and the entrypoint copies it into
  `/var/www/html` at start-up. Overriding `command:` skips that, so stage it
  first: `cp -rn /usr/src/wordpress/. /var/www/html/`. Without this,
  `wp-load.php` does not exist.
- `wp-config.php` is generated by the entrypoint, which is likewise skipped.
  Write a minimal one that reads secrets through `getenv()` so they never land
  in a file. Redis constants are required or the baked-in `object-cache.php`
  drop-in has nothing to connect with.

The stock `wordpress:cli-php8.3` image is not usable here because it runs with
`--skip-plugins`.

## Matching strategy

WordPress rewrites filenames on upload, so matching cannot be literal. Names
were reduced to a comparable stem: lowercase, strip `-scaled`, strip the
`-e<timestamp>` in-editor-edit suffix, strip `-WxH`, strip WordPress's `-1`/`-2`
collision suffix, then drop all non-alphanumerics. Extension families
(image/doc/video) still have to agree so a PDF never matches a JPEG.

Two traps worth remembering:

- Stripping *any* trailing number folds `IMG_8040` and `IMG_2897` onto the same
  stem and produces confident nonsense. Only strip `-\d{1,2}`.
- Candidates that are themselves thumbnails must rank last, or a `-300x200`
  file gets restored in place of an original and silently downgrades the page.

Matches were then tiered, and only tiers 1–2 treated as automatic:

| Tier | Basis | Count |
|---|---|---|
| 1 | Exact path under `WordPress Media/` | 88 |
| 2 | Same year/month, normalised name | 2 |
| 3 | Name matched elsewhere — reviewed by hand | 26 |
| 4 | Local `~/Downloads` | 7 |

Tier 3 was all legitimate on inspection: the Art Night auction photos use
spaces where WordPress used dashes, the board-meeting agendas sit under
`Board Meeting Notes/…` with human-readable names, and the `sites/324/…`
governance PDFs differ from `WordPress Media/2018/08/…` only by the old
multisite prefix. Tiering also caught one bad fuzzy match that wanted to
restore a 2025 `math-challenge.png` over `2018/07/Math-Challenge-e1532935026704.jpg`.

## Library cleanup

43 redundant duplicate copies were identified across 23 groups, keeping the
copy the site actually uses. Two passes were needed:

1. **33 deleted with their files.** Every original and generated size was
   copied to `uploads/_media-cleanup-backup-20260805/` on the share first —
   necessary because in six groups the copy being removed was *higher
   resolution* than the one in use (for example a 1545x1999
   `Hoodie-White.png` dropped in favour of the 791x1024 the site references).
   That backup is still on the share; delete it once you are satisfied.

2. **6 deleted as database rows only**, keeping the files, because those rows
   share a `_wp_attached_file` with a copy that must survive. Done with
   `wp_delete_attachment( $id, true )` under
   `add_filter( 'wp_delete_file', '__return_empty_string', 99 )`, which skips
   the unlink while still running all the normal cleanup of meta, term
   relations and caches.

### The guards earned their place

A pre-delete check refused 10 of the 43, and both reasons were real:

- **Four** (`31195`, `31198`, `31209`, `31210`) are the featured images of
  **product variations**. The REST `product` collection does not expose
  variations, so a usage scan built from rendered pages and `featured_media`
  misses them completely. They are still in use by 3–9 variations each.
- **Six** are separate attachment rows pointing at the **same file on disk**
  (including `musical-theater.png` / `Musical-theater.png`, which differ only
  in case and collide on case-insensitive SMB). Force-deleting either would
  have pulled the file out from under the copy still in use.

Any future media deletion should keep these checks: `_thumbnail_id`,
`_product_image_gallery` via `FIND_IN_SET`, `post_content LIKE`, and any other
`postmeta` referencing the same relative path.
